# Design 171b: Live refresh

Live refresh makes the screen follow the repository. A watcher polls Git and the working tree once a second, reports one settled change at a time, and a small Bubble Tea component turns each change into exactly one reload, keeps the last good view when a reload fails, and says so. Five choices shape it:

- **The default view reads the working tree**, on top of `HEAD`; `--ref <rev>` reads a commit instead and follows the name as it moves (D1, D2).
- **The watcher polls with `git`**, two processes a poll, and adds no dependency; it reads no file under `.git` itself (D5).
- **The watcher and the reload alternate.** Nothing polls while a reload runs, so a slow reload never stacks: at most one reload runs, and every change that arrives during it folds into the one reload that follows.
- **The watcher has no goroutine of its own.** It is a blocking call that a Bubble Tea command runs, and a cancelled context stops it.
- **Two packages.** `internal/watch` uses the standard library alone, so it can move to tablo and serve tableaud (D6). `internal/refresh` joins it to the frame that the Tableau grid task (679b) owns.

## The model

### What the view reads

| Invocation            | Files under `.tableaux` | History, trunk and submodule pins            | Follows                                  |
|-----------------------|-------------------------|----------------------------------------------|------------------------------------------|
| `tablotui`            | The working tree        | Git, at the commit `HEAD` names              | `HEAD`, the refs, the working-tree files |
| `tablotui --ref <rev>` | The commit `<rev>` names | Git, at that commit                         | `<rev>` and the refs                     |

**The working tree by default.** A person who saves a status file sees the tableau change within about a second and a quarter, with no commit; that is what refresh is for, and the task watches `.tableaux` for that reason. The price is that the grid then describes no commit while the history still ends at `HEAD`, so an uncommitted edit shows in the grid and not in the history until its commit. `--ref HEAD` gives the committed view. The [prototype](../prototype/171b/README.md) left this open as its first finding; D1 carries it, since `VIEWS.md` gives the ref's default as "`HEAD` of the checkout".

**`--ref <rev>`** takes any revision that names one commit: a branch, a tag, a commit id, `HEAD`, `HEAD~3`. The view reads that commit and never the working tree. The watcher resolves the name again at every poll, so `--ref main` follows `main`, and a tag or a commit id stands still because it does not move. The prototype's `--follow` flag goes: one rule serves both, and it matches what tableaud's prototype does with `at=` (D2). A value that starts with a hyphen or holds `..` is a usage error; a range belongs to the history pane (0afa).

### What counts as a change

The watcher compares a `State` between polls. A change is any difference in it.

| Input                                             | Live | `--ref` | How the watcher reads it                                             |
|---------------------------------------------------|:----:|:------:|----------------------------------------------------------------------|
| The commit in view                                | yes  | yes    | `git rev-parse`                                                      |
| The branch `HEAD` names, at the same commit       | yes  | no     | The same process                                                     |
| Any branch or remote-tracking ref                 | yes  | yes    | `git for-each-ref refs/heads refs/remotes`, as a digest              |
| A file under `.tableaux` in the working tree      | yes  | no     | A walk that hashes each name, size, mode and modification time       |
| A submodule pin                                   | by its checkout's `HEAD` (ruled at review) | by its commit | The checkout's `HEAD` of each submodule the Loader reports it read on disk, one `rev-parse` each per poll |
| The index                                         | no   | no     | Not read                                                             |
| The repository breaks or heals, the ref disappears | yes | yes    | Git's error is part of the state                                     |

- **The refs.** Authorisation reads the trunk whatever the ref in view (`VIEWS.md`), so a merge to the trunk changes the marks of a view that stands on another branch. The watcher does not know the trunk's name, since `version.yaml` holds it and a front end reads no project file, so it takes every branch and remote-tracking ref. A commit on an unrelated branch therefore costs one reload that changes nothing on screen.
- **A submodule pin**, in the live view, is the `HEAD` of the submodule's checkout, as the owner ruled at review on 2026-10-06 for consistency with the working tree as the default source (4f60 decision 8); at a commit it is the gitlink in that commit's tree, as the assignment mockup states ("The four submodule pins come from the tree at `3cdae52`"). So a commit that moves a pin moves `HEAD`, which is a change, and a submodule checkout that moves is a change too: the watcher asks `rev-parse HEAD` in each submodule the Loader reports it read on disk, one process each per poll. A pin staged with `git add` is no change by itself (A9, D4).
- **The index** holds nothing the view reads. A staged file is also in the working tree, and the live view reads it there.
- **Misses.** An edit that keeps a file's size and lands inside the file system's timestamp granularity; a change that reverts inside one interval; a clone that fetches a commit a pin names without moving any ref. `Poke` reloads on demand for these (A6).

### Polling, the interval and the settle

The watcher polls. Git answers both questions through its own lookup, so loose refs, `packed-refs`, the reftable format, a detached `HEAD`, a linked worktree and a submodule need no case of their own. File-system notification needs the layout of `.git` that Git already knows (a `.git` file that names a gitdir, a common directory, a rename over `packed-refs`, directories that appear later), is not recursive, is unreliable on WSL and network mounts, and adds a dependency; it wins on latency and idle cost, which a status screen read by a person does not need.

| Constant           | Value  | Meaning                                                                 |
|--------------------|--------|-------------------------------------------------------------------------|
| `DefaultInterval`  | 1 s    | Between polls while nothing changes                                     |
| `DefaultSettle`    | 250 ms | A changed state must read the same twice, this far apart, before it counts |
| `DefaultMaxSettle` | 2 s    | After this long without two equal reads, the watcher reports the latest |

No flag sets them. A change reaches the screen at most one interval, one settle and one reload after it happens. A burst, such as a commit that rewrites several files or a rebase, yields one report. A stream of changes that never rests yields a report every two seconds.

### Package `internal/watch`

```go
// Package watch reports when the inputs of a Tableaux view change. It uses the
// standard library and the git executable, and it reads no file under .tableaux.
package watch

const (
	DefaultInterval  = time.Second
	DefaultSettle    = 250 * time.Millisecond
	DefaultMaxSettle = 2 * time.Second
)

// ErrUsage marks an error of Open that the command reports with exit status 2.
var ErrUsage = errors.New("usage")

// Source says what the view reads.
type Source struct {
	Dir string // the project directory, absolute: the one that holds .tableaux
	Ref string // the revision --ref names; empty for the working tree on HEAD
}

// Live reports whether the view reads the working tree.
func (s Source) Live() bool

// Open checks the flags and returns the source. It makes dir absolute. When at
// starts with a hyphen or holds "..", it wraps ErrUsage as "usage: --ref <ref>:
// name one commit". It fails when dir is not inside a Git repository ("<dir>:
// <git's message>") or when at names no commit ("--ref <ref>: no such commit").
func Open(ctx context.Context, dir, at string) (Source, error)

// State is what a load reads, in a form that two polls compare with ==.
type State struct {
	Commit string // the commit in view, 40 or 64 hexadecimal digits
	Branch string // live: the branch HEAD names; empty when detached or with --ref
	Refs   string // the SHA-256, in hexadecimal, of the for-each-ref output
	Tree   string // live: the digest of .tableaux, or "absent"; empty with --ref
	Err    string // git's message when the commit does not resolve; the other fields are then empty
}

// Clock is the time the watcher sleeps on. A test supplies its own.
type Clock interface {
	Now() time.Time
	After(d time.Duration) <-chan time.Time
}

// Watcher polls one source. The zero value is not usable; call New.
type Watcher struct {
	Source    Source
	Interval  time.Duration
	Settle    time.Duration
	MaxSettle time.Duration
	Clock     Clock
	// unexported: poke chan struct{} with capacity 1, and
	// run func(ctx context.Context, dir string, args ...string) (string, error),
	// the git runner, which a test in the package wraps to count processes.
}

// New returns a watcher with the default timings and the system clock.
func New(src Source) *Watcher

// Snapshot reads the state once. It never fails: an error becomes State.Err.
func (w *Watcher) Snapshot(ctx context.Context) State

// Next blocks until the state differs from prev and has settled, or until a
// poke, and returns it. It returns prev and the context's error when cancelled.
func (w *Watcher) Next(ctx context.Context, prev State) (State, error)

// Poke makes the Next that waits now, or the next one called, return the
// current state at once, changed or not. It never blocks; pokes do not queue.
func (w *Watcher) Poke()
```

**`Snapshot`** runs two processes, each as `git -C <Dir> …` with `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C` added to the environment, under `exec.CommandContext`:

1. Live: `rev-parse HEAD --abbrev-ref HEAD`, which prints the commit and then the branch, or `HEAD` when detached, which becomes the empty `Branch`. With `--ref`: `rev-parse --verify --end-of-options <Ref>^{commit}`.
2. `for-each-ref --format=%(objectname) %(refname) refs/heads refs/remotes`, hashed whole.

When either fails, the state is `State{Err: msg}`, where `msg` is the first line of git's standard error without a leading `fatal: `. Live, it then walks `<Dir>/.tableaux` with `filepath.WalkDir` and hashes one line per entry: for a directory its slash-separated relative path and `d`; for any other entry its path, size, modification time in nanoseconds and mode in octal. It skips an entry that vanishes during the walk, follows no symbolic link, and returns `absent` when the directory does not exist.

**`Next`** runs this loop:

1. If a poke waits, take it, and return `Snapshot` at once.
2. Read `cur`. If `cur` equals `prev`, go to step 5.
3. Settle: wait `Settle` on the clock, read again, and repeat while the two reads differ and the waits total less than `MaxSettle`. `cur` is the last read.
4. If `cur` differs from `prev`, return it. A change that reverts while it settles reports nothing.
5. Wait for the first of: the context's end, a poke (go to step 1) or `Interval` on the clock (go to step 2).

After every read and in every wait, a cancelled context returns `prev` and the context's error.

### Package `internal/refresh`

```go
// Package refresh joins a watcher to a Bubble Tea frame: one load per settled
// change, never two at once, and the last good view kept when a load fails.
package refresh

// Watcher is what the component needs of *watch.Watcher. A test scripts it.
type Watcher interface {
	Snapshot(ctx context.Context) watch.State
	Next(ctx context.Context, prev watch.State) (watch.State, error)
	Poke()
}

// Loader loads the view data for one settled state. The frame supplies it. It
// runs in a command's goroutine, and st.Err is always empty when it runs.
type Loader[T any] func(ctx context.Context, st watch.State) (T, error)

// Loaded is the one message the frame handles. It carries the result of one load.
type Loaded[T any] struct {
	State watch.State // the state the load read
	Data  T           // the view data; the zero value when Err is set
	Err   error       // why the load failed; the frame then keeps what it shows
}

// Status is what the frame says about the source and the last load.
type Status struct {
	Source  watch.Source
	State   watch.State // the state of the last good load
	Good    bool        // a load has succeeded
	Loaded  time.Time   // when the last good load finished
	Loading bool        // a load runs now
	Err     error       // the latest load's failure; nil after a good load
	Failed  time.Time   // when the present run of failures began
}

// Where names the source in one phrase, in the mockups' form "main at 3cdae52".
func (s Status) Where() string

// Notice is the line the frame adds while there is no view or a stale one; it
// is empty when the view is current.
func (s Status) Notice() string

// Model is the component. It is a value, as a Bubbles component is.
type Model[T any] struct{ /* ctx, src, w, load, now, status */ }

// New returns the component. now is the clock's Now.
func New[T any](ctx context.Context, src watch.Source, w Watcher, now func() time.Time, load Loader[T]) Model[T]

// Init returns the command that reads the first state.
func (m Model[T]) Init() tea.Cmd

// Update handles the component's own messages and ignores every other.
func (m Model[T]) Update(msg tea.Msg) (Model[T], tea.Cmd)

// Force reloads now, or as soon as the running load ends. It calls Poke.
func (m Model[T]) Force()

// Status returns the status.
func (m Model[T]) Status() Status
```

**The alternation.** The component has two messages: the unexported `changed{state watch.State}` and `Loaded[T]`. Exactly one command is outstanding at any time. At review on 2026-10-06 the owner fixed `T` as the snapshot tablo's library loads once per change: the frame stores it on a good load and broadcasts its `ReloadMsg`, and each pane derives its view from the stored snapshot in process (679b A9), so one load serves every pane.

| On                     | The component                                                                                   | Returns                              |
|------------------------|-------------------------------------------------------------------------------------------------|--------------------------------------|
| `Init`                 | —                                                                                               | A command: `Snapshot`, then `changed` |
| `changed`              | Sets `Loading`                                                                                  | The load command for that state      |
| `Loaded`, `Err` nil    | Clears `Loading` and `Err`; sets `Good`, `State` and `Loaded`                                   | The wait command: `Next(ctx, msg.State)`, then `changed` |
| `Loaded`, `Err` set    | Clears `Loading`; sets `Err`; sets `Failed` if `Err` is nil before; keeps `Good`, `State` and `Loaded` | The same wait command                |
| Any other message      | Nothing                                                                                         | `nil`                                |

The load command calls the `Loader`, except for a state with `Err`, which it turns into `Loaded{State, Err: errors.New(State.Err)}` without a call. The wait command arms against the state the load read, not the state of the last good view, so a failure does not reload in a loop, and the fix, which changes the state again, reloads once. A command that finds the context cancelled returns `nil`, which Bubble Tea drops.

**A slow reload.** While a load runs, no wait runs, so nothing polls and no change queues. When the load ends, `Next` reads at once, finds whatever changed meanwhile, settles and reports it as one change. When a load reads files a moment newer than its state, one more load of the same files follows, which is redundant and harmless. The prototype's sequence numbers and its watcher that ran beside the load go.

**The screen while the project is invalid.** A load fails when the `Loader` returns an error (A7) or the state carries `Err`. The frame then keeps every row it shows, and the component says so:

| `Good` | `Err` | `Where`                                             | `Notice`                                                             |
|:------:|:-----:|-----------------------------------------------------|----------------------------------------------------------------------|
| no     | nil   | `working tree`, or the `--ref` value                 | `Loading`                                                            |
| no     | set   | The same                                            | `No view yet: <message>`                                             |
| yes    | nil   | `working tree on <branch> at <commit>`; detached, `working tree at <commit>, detached`; with `--ref`, `<rev> at <commit>` | Empty |
| yes    | set   | The same, for the last good state                   | `Reload failed at <Failed>, showing the view of <Loaded>: <message>` |

`<commit>` is the first seven digits, `<message>` the first line of the error, and each time prints as `15:04:05` in local time. [`171b/lines.txt`](171b/lines.txt) holds nine cases. The first load that fails leaves the program running with `No view yet`, and the watcher brings the view as soon as the project loads. A reload in progress shows nothing: the view on screen stays until the new one replaces it.

### The command line, errors and exit

`--ref <rev>` is this task's one option; `-C <dir>` and the option parsing belong to the frame (A2). Before the program takes the screen, the command calls `watch.Open`: an error that wraps `ErrUsage` prints `tablotui: <error>` to standard error and exits 2, and any other prints the same and exits 3, the codes tablo's plumbing uses for usage and for a failure to read. After the start nothing exits the program but the viewer: every later failure is a `Notice`.

**How the watcher stops.** The command creates one context, hands it to `refresh.New`, and cancels it when `Program.Run` returns. The waiting `Next` returns, a git process in flight dies with its context, and the load receives the same cancellation. No goroutine belongs to the watcher, so nothing remains to join.

### Cost

One poll costs two git processes and one `lstat` per entry under `.tableaux`. Measured with a trial of this design on this machine (Linux on WSL2, Git 2.47.3): 3.5 ms on the umbrella repository (74 entries, 3 refs); 7.5 ms with 5 000 packed branches and 26 ms with 5 000 loose ones. Neither process reads the index or the working tree, so the cost does not grow with the repository's files. An idle program therefore spends about 3.5 ms of processor time each second on such a repository. One reload costs one `Loader` call (A8). Nothing here is deterministic in time; everything is deterministic in order, which the tests drive.

## Tests

The watcher tests build repositories with the real `git` in `t.TempDir()`, with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to the null device and a fixed identity. No test sleeps or reads the system clock. A test clock announces each wait the watcher asks for and releases it on the test's word, so a test knows which wait the watcher stands in before it acts:

```go
// Clock is the test clock of internal/watch/watchtest.
type Clock struct {
	Asked chan time.Duration // receives the duration of each After call; capacity 64
	Tick  chan time.Time     // After returns it; a send releases the one waiter
	T     time.Time          // what Now returns
}
```

A change test reads `Interval` from `Asked`, acts on the repository, sends a tick, reads `Settle` from `Asked`, sends a tick, and receives the state from `Next`. A no-change test acts, sends a tick, and reads `Interval` from `Asked` again with nothing delivered.

## Decisions at review

The owner decided each question this design raised on 2026-10-06, together with the cross-design rulings of that review; a decision the review did not reach stands as the design states it, accepted with the design.

1. **The working tree by default.** Decided by the owner on 2026-10-06: the live view reads the files under `.tableaux` from the working tree, and `--ref HEAD` gives the committed view; tablo's 4ed9 decision 4 and tableaud's 49ce decision 3 state the same, and VIEWS.md's parameter table changes from "`HEAD` of the checkout" to the working tree. The alternative read `HEAD` only and watched no file, so a saved edit showed after its commit. The choice binds tableaud's Server (49ce), tablo's Loader (4f60) through A9, and the frame (679b).
2. **The ref option follows the name.** Accepted with the design, as stated: `--ref main` moves with `main`; a tag or a commit id stands still. The alternative fixes the commit at the start and adds a `--follow` flag for the other behaviour, as the prototype did.
3. **The option's name.** Decided by the owner on 2026-10-06, for the alternative: `--ref`, as tablo and tabloio use it, for one vocabulary across the four tools (4ed9 decision 3); the text reads so throughout, and this repository's README changes now. The design was written with `--at`, as the README and tableaud's `at` query named it.
4. **A pin shows at its commit.** Decided by the owner on 2026-10-06, for the alternative: in the live view a submodule reads at its checkout's `HEAD`, for consistency with decision 1 (4f60 decision 8), so the umbrella's live view follows work inside a subproject as it happens; the watcher asks `rev-parse HEAD` in each submodule the Loader reports it read on disk, one process each per poll. A pin staged and not committed is still no change by itself. At a commit the pin is the gitlink in that commit's tree. The design's text, A9 and T6 read so.
5. **Polling, at one second.** Accepted with the design, as stated: the watcher polls with git every second and settles for 250 ms, with no option and no dependency. The alternative adds `fsnotify` for latency and idle cost and keeps the poll as the fallback.
6. **One watcher for two projects.** Decided by the owner on 2026-10-06, for the alternative in this wave: each project keeps its own watcher, this one under `internal/watch` here and tableaud's digest under its `internal/serve`, since the two loops differ, a server asking on request and a terminal waiting, and the mechanisms differ with them. What the two share is the specification: one list of what counts as a change, which T6 here and 49ce's T13 both test, now including a submodule checkout that moves. A repository digest exported by tablo may replace both later, once the Loader reports what it read; no task is added for it now.
7. **What the component hands the frame.** Decided by the owner on 2026-10-06: `T` is the snapshot tablo's library loads once per change; the frame stores a good snapshot and broadcasts its `ReloadMsg`, and each pane derives its view from it in process (679b decision 11). The alternation and the error rule here hold; 679b's sequence numbers serve a parameter change alone. The task file now requires `679b` from implementation to integrate, as [The plan](#implementation-notes) asked; the cross-project requirement on tablo's Loader waits there until the commit it must name exists, as README.md now allows.
